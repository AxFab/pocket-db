# ADR 0013: 12-Byte ObjectId-Style Document Identifiers

## Status

Accepted (V1).

## Context

Every document needs an `_id`, unique within its collection, that Pocket DB
can generate automatically on insert or accept from the caller. Common
choices for an embedded document database include:

- A random UUID (v4), typically 16 bytes / 36-character string form.
- A monotonic integer counter per collection.
- A compact, structured id combining a timestamp with randomness and a
  counter — the scheme MongoDB popularized as `ObjectId`.

The design explicitly draws on both SQLite (single-file, embedded) and
MongoDB (document model, familiar API) as reference points (see the Project
Synopsis). The id format is one of the places that inspiration was carried
through directly rather than reinvented.

## Decision

Use a 12-byte, MongoDB-compatible `ObjectId` layout, exposed as a
24-character lowercase hex string:

```text
4 bytes   unix timestamp, seconds, big-endian
5 bytes   process-random (fixed per process lifetime)
3 bytes   monotonic counter, big-endian, wraps at 0xFFFFFF
```

- The **timestamp** component means ids sort roughly chronologically by
  creation time even though Pocket DB has no dedicated sorted id index —
  lexicographic ordering of the hex string tracks insertion order at
  second resolution.
- The **process-random** component (5 bytes, generated once and held fixed
  for the process's lifetime) differentiates ids generated by different
  processes without requiring any coordination between them — important
  given Pocket DB's single-process-per-file model
  ([ADR 0010](0010-single-process-file-lock.md)) still allows different
  processes to write to *different* database files, or the same logical id
  space to be merged from multiple sources later.
- The **counter** (3 bytes, monotonic, wraps at `0xFFFFFF`) differentiates
  ids generated within the same second by the same process — the timestamp
  alone only has 1-second resolution, so a burst of inserts needs a
  tiebreaker.
- User-supplied `_id` values are validated against
  `/^[0-9a-f]{24}$/` on insert — an id must have this exact 24-hex-character
  shape, matching the internal encoding, even though Pocket DB does not
  itself re-derive or re-validate the timestamp/random/counter substructure
  of a caller-provided id.
- All multi-byte integer fields within the id follow the project's general
  big-endian convention (see [ADR 0002](0002-binary-file-format.md)).

## Consequences

- Collisions are extremely unlikely without any global coordination:
  same-process collisions are ruled out structurally by the monotonic
  counter, and cross-process collisions would require both an identical
  process-random value (a 40-bit space) and the same second and counter
  value — a combination this scheme treats as acceptably improbable, the
  same tradeoff MongoDB's `ObjectId` makes.
- 12 bytes (24 hex characters) is more compact than a UUID's 16 bytes
  (36-character string form with hyphens) while carrying more structure
  (embedded creation time) than a random UUID does — ids are smaller both
  on disk (in every `put1` payload, see
  [ADR 0002](0002-binary-file-format.md)) and as map keys in the primary
  index (`Map<string, {id, offset}>`, see `indexes.md`).
- Choosing a well-known, MongoDB-compatible layout means developers coming
  from MongoDB (a large fraction of the document-database-familiar
  audience Pocket DB targets, per the Project Synopsis) recognize the id
  shape immediately, and off-the-shelf ObjectId tooling/parsers from that
  ecosystem can decode Pocket DB ids without modification.
- The id encodes a *creation* timestamp, not a last-modified time — because
  `_id` is immutable (`$set`/`$unset`/`$currentDate`/`$rename` on `_id` all
  throw, enforced by `assertUpdateDoesNotMutateId`), this timestamp is
  permanently accurate for the document's original insertion, which can be
  useful for cheap approximate "created around when" queries without a
  dedicated field, at the cost of that information only being extractable
  by decoding the hex string manually — Pocket DB exposes no built-in
  helper for pulling the timestamp back out of an `_id` in V1.
- Second-resolution timestamps mean the id alone cannot express sub-second
  creation order across different processes (only the per-process counter
  orders same-second, same-process inserts) — acceptable because ordering
  guarantees are not a stated goal of `_id`, only unmodified.
- This is purely an identifier-generation and validation decision; it has
  no bearing on how ids are indexed or looked up — that is entirely the
  primary index's concern (`InMemoryPrimaryIndex`, a plain hex-string-keyed
  `Map`, out of scope for this ADR).

## Alternatives Considered

- **Random UUID v4** — rejected: no embedded creation-time signal, larger
  on-disk footprint per id, and no natural chronological sortability. Would
  still need a comparably-sized random space to achieve similar collision
  resistance without the timestamp/counter structure's cheaper guarantees.
- **Monotonic integer counter (per collection or global)** — rejected:
  requires either a durable counter (itself needing persistence and replay
  handling — extra state and a chicken-and-egg problem with
  [ADR 0003](0003-replay-based-startup.md)'s replay-rebuilds-everything
  model) or a non-durable in-memory counter that would produce colliding
  ids after certain crash/restart sequences unless carefully reconciled
  against the log on replay.
- **Application-supplied ids only (no auto-generation)** — rejected as the
  sole mechanism: many of Pocket DB's target use cases (prototypes, local
  caches, quick scripts) benefit from "just insert, id is handled for you"
  ergonomics matching MongoDB's familiar API, though caller-supplied ids
  remain fully supported alongside auto-generation.
- **Shorter identifiers (e.g. 8-byte random)** — rejected: would shrink
  per-record overhead further but at meaningfully higher collision risk for
  a given id volume, and would abandon the embedded-timestamp property that
  the 12-byte MongoDB-style layout provides for free.
